# テスト計画

> 状態: 下書き（実装しながら育てる。各フェーズで具体的なテストを追記する）

## 目的
品質を確かめる方法を定める。合否の基準は requirements.md（受け入れ条件）と non-functional.md（数値の目標）に従う。

## 決定済み
- テストは4段階：単体 → 結合 → E2E → 負荷試験・実機リハーサル
- 単体・結合テストは Vitest で行う。結合テストは `@cloudflare/vitest-plugin`（旧名 `@cloudflare/vitest-pool-workers`）を使い、本番と同じ workerd 上で Agent を動かす
- E2E テストは Playwright で行う（複数のブラウザのタブで、司会・投影・参加者を同時に動かす）
- 各フェーズは、そのフェーズのテストが通ったらコミットする
- 負荷試験は Node のスクリプト（`load/load-test.mts`）で行い、本番の Worker に向けて実施する（2026-11-01 に決定）

### 1-1. テストの土台（Phase 2）
- `pnpm test` で `test/**/*.test.ts` と `src/**/*.test.ts` を workerd 上で実行する（`vitest.config.mts`）
- テスト用のエントリ `test/worker.ts` は Agent だけを export する（OpenNext のビルドなしでテストできる）
- WebSocket で Agent につなぐ道具：`test/helpers/agent-socket.ts`（`connectAgent(agent, name)` → `call()`・`waitFor()`）
- ハイバネーションは `cloudflare:test` の `evictDurableObject(stub, { webSockets: "hibernate" })` で再現できる
- `test/smoke.test.ts`：接続・callable・役割の記録・ハイバネーション後の役割・クライアントからの state 書き換えの拒否・Agent どうしの呼び出し

### 2. 単体テスト（Phase 3）
game-rules.md の各項目を、そのままテストにする。

| 対象 | 確かめること |
|---|---|
| カード生成 | 列ごとの範囲（B1–15…O61–75）、列の中で番号が重ならない、中央が FREE |
| 抽選 | 同じ番号が出ない、75回で引き切る、76回目は引けない |
| ライン判定 | 横5・縦5・斜め2の12本、FREE を含めて判定する |
| リーチ | あと1マスのライン数を正しく数える。ビンゴ済みの人はリーチに数えない |
| ビンゴと順位 | 何回目でビンゴしたか、同じ回は同着、次の順位は人数分下がる（1位が2人なら次は3位） |
| 途中参加のカード | 参加した時点でビンゴになっていない（何度作っても）。どこかの列を引き切ったら受付終了 |
| 参加コード | 6文字・使う31文字だけ・重ならない。入力の正規化（小文字・ハイフン・空白） |
| 入力チェック | ニックネーム1〜20文字・ルーム名1〜40文字、前後の空白と制御文字を除く |
| CSV | BOM 付き、`= + - @` で始まる値の前に `'` が付く |

- 乱数を使う関数は、乱数を外から渡せるようにして、結果を固定してテストする

#### 2-1. 実装したテスト（Phase 3）
- テストは `test/lib/*.test.ts`。乱数を固定する道具は `test/helpers/seeded-random.ts`（`seededRandom(seed)`）
- 本番の乱数は `src/lib/random.ts` の `cryptoRandomInt`（`crypto.getRandomValues`。偏りが出ないよう端数を捨ててやり直す）

| ファイル | 対象（`src/lib/`） |
|---|---|
| `bingo.test.ts` | `bingo.ts`：カード生成・抽選・マーク・ライン・リーチ・ビンゴと順位（`judgeAll`）・途中参加のカード（`generateLateJoinCard`） |
| `join-code.test.ts` | `join-code.ts`（生成・正規化・表示用の区切り）、`ids.ts`（ルーム ID・司会トークン・参加者 ID） |

| `csv.test.ts` | `csv.ts`：BOM・CRLF・式の対策・クォート |

- 参加コード：`generateJoinCode` の既存のコードには、無効（revoked）のコードも含めて渡す（同じコードを二度発行しないため。Phase 4）
- 順位：`judgeAll` には「これまでにビンゴした人数（削除された人も含む）」を渡す。Agent はこの人数を保存しておく（Phase 4）
- 途中参加のカード：普通に作ってビンゴでないものを探し（100回まで）、なければ各ラインに未抽選の番号を1つずつ置いて作る。どこかの列の番号がすべて引かれていると（`isLateJoinClosed`）、どう作ってもビンゴになるので `null` を返す。このとき BingoRoom は `LATE_JOIN_CLOSED` を返す（game-rules 7章）
- CSV の列の並びは Phase 4（`exportResults`）で決める。Phase 3 は書き出しの共通部分だけ

### 3. 結合テスト（Phase 4・5）

#### 3-0. 実装したテスト（Phase 4）
- `test/bingo-room.test.ts`：下の表のシナリオのうち BingoRoom の分（RoomDirectory の一覧・合言葉は Phase 5）。ほかに、初期化していないルームの拒否、状態ごとのエラー、コードの上限、listCodes、CSV、RoomDirectory への通知、ハイバネーション後の配信、切断したときのオフライン表示
- `test/lib/room-helpers.test.ts`：試行回数の制限・秘密の値の比較・ニックネームの比較・結果の並びと CSV（`src/lib/` の純粋関数）
- テスト用の道具：`test/helpers/room.ts`（`createRoom`・`connectHost`・`connectPlayer`・`issueCodes`）。`test/worker.ts` の BingoRoom は、時計を進める（`testAdvance`）、次の番号・カードを決める（`testSetNextNumbers`・`testSetNextCards`）、スケジュールを読む（`testSchedules`）ことができる
- `test/room-directory.test.ts`（Phase 5）：合言葉（違う合言葉・締め出し・`main` 以外の拒否）、作成と司会用 URL、一覧の並びと状態の更新、自動削除で一覧から消えること、URL の作り直し、削除（確認のルーム名・ゲーム中・開始前と終了後）。テストの合言葉は `vitest.config.mts` で設定し、接続元はテストごとに別の IP（`CF-Connecting-IP`）にする
- 自動削除は、時計を進めてから `checkExpiry` を直接呼んで確かめる（スケジュールが予約されていることは `testSchedules` で別に確かめる）
- `destroy()` のあと、テストのログに `broken.outputGateBroken; jsg.Error: destroyed` が出るのは正常（api.md 7章）

api.md の callable・メッセージ・エラーを1つずつ確かめる。主なシナリオは次のとおり。

| シナリオ | 確かめること | 関係する機能 |
|---|---|---|
| 参加の流れ | 未使用のコードで参加 → 使用済みになる → 同じコードで復帰すると同じカード | F-20, F-21 |
| 参加の失敗 | 未発行・無効なコード、重なるニックネーム、101人目、終了後、途中参加の受付終了後（使用済みのコードでの復帰はできる） → それぞれ正しいエラー | F-17, F-20 |
| 抽選の流れ | 開始 → 抽選で公開 state が全員に届く → 本人にだけ `player:self`、司会にだけ `host:participants` が届く | F-04, F-05 |
| 抽選の連打 | 3秒以内の2回目は `COOLDOWN`。2つの司会接続からほぼ同時に呼んでも番号は1つ | F-05 |
| 権限 | 司会でない接続から司会の操作 → `FORBIDDEN`。違うトークン → `BAD_TOKEN`。違う合言葉 → `BAD_PASSPHRASE` | security 1章 |
| 試行回数の制限 | 間違いが続いたら `RATE_LIMITED` | security 2-2 |
| 接続していない人の当選 | 参加者の接続を切ったまま抽選 → ビンゴと順位が記録され、再接続したときに受け取る | F-23, F-24 |
| 削除と差し替え | 参加者の削除・コードの差し替え・司会トークンの作り直しで、古い接続が切られ、古い値が使えなくなる | F-08, F-11, F-40 |
| 自動削除 | 終了から7日・放置30日で削除され、一覧からも消える（時刻を進めて確かめる） | F-15, F-18 |
| 公開 state の中身 | 公開 state に、司会トークン・参加コード・カード・ビンゴしていない人の名前が入っていない | security 1章 |

| シナリオ | 内容 |
|---|---|
| 本番の流れ | 管理画面でルーム作成 → コード発行 → 投影画面を開く → 参加者3人が参加 → 開始 → 抽選を繰り返してビンゴ → 終了 → CSV |

#### 4-1. 実装したテスト（Phase 6）
- `e2e/bingo.spec.ts`：上の表の5つのシナリオ。道具は `e2e/helpers.ts`（ルーム作成・コード発行・参加・抽選）
- 動かし方：`pnpm test:e2e`。`pnpm preview`（:8787）を自動で起動する（起動済みならそれを使う）。管理画面の合言葉は `.dev.vars` の `ADMIN_PASSPHRASE` を読む（環境変数 `E2E_ADMIN_PASSPHRASE` があればそちら）
- 端末ごとに別のブラウザコンテキストを使う（保存した参加コード・司会トークンが混ざらないように）
- 再接続：Chromium のオフライン切り替え（`setOffline`）では、開いている WebSocket は切れない。そのため `routeWebSocket` で接続を仲介し、テストから切断・接続の拒否をする（`networkSwitch`）。拒否には 4000 番台を使わない（クライアントがつなぎ直しを諦めるため）
- 本番の流れ：抽選は3秒に1回なので、ビンゴが出るまで引くと2〜3分かかる。テストの時間の上限は8分
- Chromium の依存ライブラリは `pnpm exec playwright install --with-deps chromium` で入れる（`.devcontainer/post-create.sh`）

### 5. 負荷試験（Phase 7）
- 本番と同じ環境（Cloudflare 上）にテスト用のルームを作り、スクリプトで **110接続**（参加者100＋司会・投影など）を張る
- 抽選を75回行い、次の値を記録する
  - 司会が抽選してから、全接続が受け取るまでの時間 → **全員が1秒以内**（目標）、**2秒以内**（上限）
  - 1接続あたりの受信量 → **1ゲームで数百 KB 以内**
  - 取りこぼし（受け取れなかった抽選）→ **0件**
- 途中で一部の接続を切ってつなぎ直し、最新の状態に追いつくことも確かめる
- Cloudflare の利用量を見て、無料プランの上限まで余裕があるかを確かめる（料金プランの判断に使う）

#### 5-1. 実施方法（Phase 7）
- スクリプト：`load/load-test.mts`。画面と同じ通信（WebSocket＋callable）を使い、管理画面と同じ手順でルームを作る → 司会が名乗って参加コードを100枚発行 → 投影9＋参加者100がつないで参加 → 開始 → 抽選75回 → 終了 → ルームを削除
- 動かし方
  - 手元：`pnpm preview` を起動してから `pnpm load-test`（合言葉は `.dev.vars`）
  - 本番：`pnpm load-test https://bingo.example.workers.dev`（合言葉は `.dev.vars.production` の `ADMIN_PASSPHRASE`。このファイルはコミットしない）
  - 規模は環境変数で変えられる（`LOAD_PLAYERS` `LOAD_SCREENS` `LOAD_DRAWS` `LOAD_RECONNECT`）
- 測り方
  - すべての接続を1つのプロセスで動かし、「司会が draw を送った時刻」から「各接続に `drawn` が増えた state が届いた時刻」までを、同じ時計で測る（演出の時間は含めない）
  - 5秒たっても届かなかった接続を「取りこぼし」と数える
  - 受信量は、各接続が受け取ったフレームの合計（UTF-8 のバイト数）。参加の前から終了までの1ゲーム分
  - 再接続：20回目の抽選の前に参加者10人の接続を切り、25回目の前に新しい接続で `resume` する。復帰でき、24回目まで追いついているかを見る
  - 結果は画面に出し、`load/results/<日時>.json` にも残す（コミットしない。数値はこの表に書き写す）
- 合否：全員に届くまでの時間の最大が2秒以内、取りこぼし0件、参加者の受信量が1MB 未満、再接続した全員が復帰して追いつく
- 1台の PC から110接続を張るので、測った時間には PC 側の処理の時間も含まれる（実際の会場より厳しめになる）

#### 5-2. 結果
| 日付 | 相手 | 届くまで p50／p95／最大 | 1秒超・2秒超の抽選 | 取りこぼし | 受信量（参加者 平均／最大・投影・司会） | 再接続 | 判定 |
|---|---|---|---|---|---|---|---|
| 2026-11-01 | 手元（`pnpm preview`） | 45／66／95ms | 0回・0回 | 0件 | 204／214KB・213KB・1.6MB | 10人とも復帰・追いついた | 合格 |

- 参加者の受信量の多くは公開 state（約1KB）を、参加者が増えるたび・抽選のたびに全員へ送る分（100人の参加で約100回＋抽選75回）。基準（数百KB 以内）は満たしている
